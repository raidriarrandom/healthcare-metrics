# Solution Design Document: Healthcare Staffing Metrics Pipeline

## 1. Problem

Management wants one view of nursing home staffing and operations: nurse-to-patient ratios, hours worked,
contract (agency) dependence, occupancy, and how staffing relates to outcomes such as readmissions, delivered as an
interactive dashboard. Source data arrives as CSV files in a Google Drive folder. The project constraints:
**AWS services only** and **incremental ingestion from Google Drive**.

## 2. Architecture

![Architecture](architecture.png)

Editable diagram: `architecture.drawio` (generated by `scripts/generate_architecture_diagram.py`).

A **medallion data lake** on S3 with three layers, orchestrated by one Glue Workflow:

| Step | Component | What it does |
|---|---|---|
| Schedule | Glue Workflow `healthcare-daily-pipeline`, trigger `cron(0 13 * * ? *)` | Starts the pipeline daily at 06:00 PT; each next step starts only if the previous one SUCCEEDED |
| Ingest | Glue Python shell `healthcare-drive-ingest` | Lists the Drive folder through the Drive API (service account from Secrets Manager); downloads only new or changed CSVs (md5 vs manifest); streams them to `Bronze/` |
| Clean | Glue Spark `healthcare-bronze-to-silver` | Each Bronze file not yet processed → cleaned Parquet in `Silver/` (rules in the data dictionary) |
| Model | Glue Spark `healthcare-silver-gold` | Spark SQL builds `gold_daily_staffing` and `gold_facility_metrics`; skipped if Silver did not change |
| Catalog | Glue Crawlers (bronze, silver, gold) | Keep the Glue Data Catalog in sync so new files become queryable tables with no manual DDL |
| Serve | Athena workgroup `healthcare-analytics` + 4 views | Serverless SQL over Gold; views hold the metric logic once for every consumer |
| Visualize | Streamlit (`dashboard/app.py`) | Interactive dashboard; queries Athena views through boto3 |
| Operate | CloudWatch Logs, IAM role `healthcare-project-glue-role` | Logs for every run; the role can only touch this bucket, the Glue assets bucket and the one secret |

## 3. Why each technology (the "WHY")

| Choice | Why | Alternatives considered |
|---|---|---|
| **S3** as the lake | Cheap, durable, unlimited; decouples storage from compute; every AWS analytics service reads it | RDS/Redshift as the first landing zone: pays for always-on compute just to hold raw files |
| **Medallion layers** (Bronze/Silver/Gold) | Bronze keeps the untouched source, so any bug can be fixed by reprocessing; Silver is cleaned once and reused; Gold is shaped for questions | One "processed" layer: no replay if the cleaning logic changes |
| **Glue Python shell** for ingestion | The Drive download is plain Python (Google API client), no Spark needed; Python shell costs 1/16 DPU; no 15-minute limit (the 220 MB PBJ file is streamed); lives in the same Workflow as the other jobs | **Lambda** (the first design): works for small files but the 15-minute timeout and /tmp size make big Drive files risky, and it needs a separate EventBridge rule outside the Glue Workflow |
| **Incremental by md5 manifest** | Google Drive gives each file an md5Checksum; comparing it to `_state/drive_manifest.json` means unchanged files are never downloaded again, and edited files are. Manifest is written last, so a failed upload is retried next run | Drive `modifiedTime` only: changes when metadata changes. Full reload every day: re-copies 330 MB for nothing |
| **Glue Spark (PySpark)** for transforms | 1.3 M PBJ rows plus 266 K MDS rows; Spark handles the CSV encoding (Windows-1252), type inference and Parquet writes at scale; serverless, billed per second | Pandas in Lambda: memory limit; EMR: a cluster to manage for a 2-minute job |
| **Parquet** | Columnar + compressed: PBJ went from 220 MB CSV to ~36 MB; Athena scans only the columns a query uses, so queries are faster and cheaper | CSV everywhere: Athena would scan the full file on every query |
| **Glue Data Catalog + Crawlers** | One schema store shared by Athena and Glue; crawlers register new tables automatically when a new file is dropped in Drive | Hand-written `CREATE TABLE` per file |
| **Athena** as the warehouse | Serverless SQL directly on S3 Gold, pay per TB scanned (this project scans MBs); no database to run or patch | Redshift: always-on cost not justified for ~15 K facilities × 91 days; RDS: would require loading data out of the lake |
| **Athena views** | Metric definitions (weighted HPRD, occupancy, contract share) live in SQL once; the dashboard and `run_metrics.py` cannot disagree | Calculating in the dashboard: logic duplicated, untestable in SQL |
| **Glue Workflow** for orchestration | Native, free, chains jobs and crawlers with success conditions, has its own run history and graph | Step Functions: more flexible but more to build for a linear 4-step chain; MWAA: an always-on Airflow environment |
| **Secrets Manager** | The Drive service-account key never appears in code or job parameters; access limited by IAM to one secret | Job parameters or environment variables: visible in the console |
| **Streamlit** dashboard | Required by the spec; Python only; charts with Plotly; reads Athena with the same helper as the scripts | QuickSight: per-user licence, outside the spec's Streamlit link |

## 4. Incremental processing, end to end

1. **Drive → Bronze:** only files whose md5 differs from the manifest; each lands in `Bronze/<table>/ingest_date=<today>/`
   (history kept, nothing overwritten).
2. **Bronze → Silver:** only Bronze objects whose S3 key + ETag are not in `_state/silver_processed.json`;
   the state is updated after each successful write. (Glue job bookmarks were not used: they only track DynamicFrame
   reads, and the PBJ file needs the DataFrame reader's `encoding` option.)
3. **Silver → Gold:** reference tables use their latest `ingest_date`; Gold is rebuilt only when the Silver state changed
   (`_state/gold_built.json`). Gold is small (~33 MB), so a full rebuild is simpler and safer than merging.
4. **New file types:** dropping any new CSV in the Drive folder creates a new Bronze/Silver table and catalog entry with
   no code change (table name derived from the file name).

## 5. Data model

Gold is a simple star-like model keyed on `ccn` (CMS Certification Number):

- `gold_daily_staffing`: fact table, one row per facility per day (91 days × ~14.5 K facilities = 1.33 M rows)
- `gold_facility_metrics`: facility-level summary with dimensions from Provider Info (name, ownership type, beds,
  ratings, turnover) and outcomes (readmissions, rehospitalization)

Column-level definitions: [`data_dictionary.md`](data_dictionary.md).

## 6. Assumptions and trade-offs

- **Nurse staffing** = RN + LPN + CNA direct-care hours. Admin and Director of Nursing hours are excluded, as in CMS's
  own HPRD definition.
- **Nurse-to-patient ratio** = nurse hours per resident day (HPRD). PBJ has hours, not headcounts or shifts, so a
  literal "nurses per patient" cannot be computed.
- **Overtime**: PBJ has no overtime field. Contract (agency) hours are used as the proxy: hours the facility could not
  cover with its own staff.
- **Occupancy** = daily census ÷ certified beds. Beds come from the Oct 2024 Provider Info snapshot while census is
  Q2 2024, so a few facilities exceed 100% (bed count changed); they are kept but clipped in charts.
- **Invalid days** (from the EDA): census 0, census > 0 with 0 nurse hours (unreported), or HPRD > 24 (impossible) are
  flagged `is_valid_day = false` and left out of every metric. That is 3,314 of 1.33 M facility-days (0.25%).
- **"Hospital"** in the spec = nursing home (skilled nursing facility) in this data; **"hospital type"** = CMS
  ownership type.
- **Single quarter**: PBJ covers Apr–Jun 2024 only, so "past year" trends are shown as daily/weekly/monthly within Q2.

## 7. Error handling, logging, security

- Every job writes to CloudWatch Logs (continuous logging on the Spark jobs); the Workflow stops the chain at the first
  failed step, and its run graph shows which step failed.
- State files are written only after the data write succeeds, so a failed run is simply retried by the next one
  (idempotent, no duplicates).
- Drive download is streamed (`upload_fileobj`) with gzip decoding, so large files never sit in memory.
- IAM least privilege: the Glue role can read/write only `healthcare-project122` and the Glue assets bucket, read only
  the `healthcare-project/drive-service-account` secret. Athena enforces its workgroup settings and a 10 GB-per-query
  scan limit.

## 8. Cost (approximate, us-west-1)

| Item | Daily run with no new files | Run with new files |
|---|---|---|
| Python shell ingest (0.0625 DPU, ~20 s) | < $0.01 | < $0.01 |
| Spark jobs (2 × G.1X, 1-min minimum each) | ~$0.03 | ~$0.10 |
| 3 crawlers | ~$0.15 | ~$0.15 |
| Athena (MBs scanned) | ~$0 | ~$0 |
| S3 (~0.6 GB) | ~$0.0005 | |

About **$5–6 per month** if left running daily. To stop it: disable the trigger `healthcare-daily-start`.
